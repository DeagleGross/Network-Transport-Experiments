# Requirement traceability

> **Status:** This table is the acceptance index for the proposal. Each requirement maps to a concrete API or SPI contract, an example or backend mapping, and a limitation or evidence gate.

| Requirement | API or SPI contract | Usage or backend demonstration | Known limitation or acceptance evidence |
|---|---|---|---|
| **R1: TCP-only and TCP+TLS; native TLS central** | `TransportEngine.Listen`/`Connect`; `TransportApplication` receive/write/ready callbacks; listener/connect TLS policy; `TransportTlsInfo` | Provider-specific examples under [examples](examples/README.md) show plaintext and TLS usage for managed Socket, epoll, io_uring, IOCP, and RIO | Native TLS is unimplemented in this proposal. TLS is provider-driven before `OnReady`, with `SslStream` available as an exact compatibility strategy. |
| **R1.5: all relevant Kestrel TLS hooks/options** | `SslServerAuthenticationOptions` remains authoritative; handshake `TransportClientHelloCallback`; async `TransportServerOptionsSelectionCallback`; separate ClientHello and handshake timeouts; structured TLS info | Full [callback parity matrix](tls.md#callback-parity-matrix), [server option matrix](tls.md#server-option-parity-matrix), and [Kestrel feature mapping](tls.md#kestrel-feature-mapping-after-authentication) | Exact `TlsHandshakeCallbackContext.SslStream` and `ISslStreamFeature` still require the real `SslStream` path. Delayed client certificate invocation needs a higher-level public adapter API not yet shaped. |
| **R2: epoll, io_uring, managed Socket fallback, Windows** | `TransportProviders` exposes typed ManagedSockets, Epoll, IoUring, WindowsIocp, and WindowsRio choices | [SocketSet API map](socketset-public-api-map.md), typed options in [api.md](api.md#typed-provider-options), and one usage file per provider | Managed Socket is the first implementation and control. IOCP is the general Windows provider; RIO is explicit and never automatic. |
| **R3: generic accept/connect/read/write/handshake SPI** | `TransportProvider` -> `TransportEngine` -> listener/connection; demand-driven `TransportListener.Accept`; synchronous submit plus callback completion; TLS configured before readiness | Full candidate surface in [api.md](api.md#proposed-reference-surface) and review in [api-review.md](api-review.md) | The callback SPI is proposed for experimental incubation. Third-party provider support remains an explicit open question. |
| **R4: fd-bound nonblocking OpenSSL** | TLS handshake raises the ClientHello callback and maps internal `WANT_READ`/`WANT_WRITE` states to provider readiness | [fd-bound OpenSSL contract](tls.md#fd-bound-openssl-contract) and [epoll TLS usage](examples/EpollTls.cs) | fd-bound OpenSSL is an internal provider implementation. No memory BIO or public ClientHello-observation method is required. |
| **R5: io_uring not prematurely narrowed** | Public usage is one TLS configuration; the provider may internally use memory BIO, fd-bound polling, `SslStream`, kTLS, or a hybrid; `TryRetainPayload` preserves selected receive storage without exposing io_uring identities | [io_uring TLS usage](examples/IoUringTls.cs), [backend models](backends.md#linux-io_uring-provider), and [integration questions](backends.md#io_uring-integration-questions) | No public strategy switch or preferred internal design is asserted. Multishot, buffer rings, retained-lease bounds, poll, cancellation, and kTLS must be compared. |
| **R6: kTLS** | `TransportTlsOffloadOptions` with independent TX/RX `Disabled`/`Prefer`/`Require`; `TransportTlsOffloadInfo` reports actual state | [kTLS contract](tls.md#ktls-and-hardware-offload), epoll and io_uring kTLS sections | Build, OS, kernel, protocol, cipher, TLS feature, and backend can prevent activation. `Require` fails; `Prefer` reports fallback. |
| **R7: ordinary NIC and optional hardware TLS offload** | No generic switch for ordinary offloads; `TlsHardwareOffloadStatus` reports `NotApplicable`, `Inactive`, `Active`, or `Unknown` | [Ordinary offload distinction](tls.md#ordinary-nic-offloads), [hardware TLS](tls.md#hardware-tls), Linux provider mapping | Runtime does not configure drivers/NICs. kTLS is not proof of NIC crypto. Zero-copy is not inferred from either. |
| **R8: reuse versus new Socket** | Managed provider composes ordinary `Socket`/SAEA behind the same callback API; connection omits raw socket surface and public read methods | [Why this is not a second Socket](README.md#why-this-is-not-a-second-socket), [managed mapping](api.md#how-the-managed-socket-provider-fits), and [SocketSet comparison](socketset-public-api-map.md) | No raw handle transfer or fabricated Socket is proposed. The stronger distinction from Socket is provider-owned callback buffers and shared engine lifetime. |
| **R9: PipeIOBridge-like adapter** | `TransportPipeEngine`, `TransportPipeListener`, and `TransportPipeConnection`; direct receive sink, retained receive, and copy fallback; pause/resume backpressure; terminal borrowed-send completion | [Pipelines adapter proposal](pipelines-adapter.md), [Pipelines/Kestrel section](README.md#pipelines-and-kestrel), and [backend mapping](backends.md#pipe-adapter-mapping) | The candidate adapter and receive-sink SPI are unimplemented and experimental. | **R10: first-class clients and Redis-style long-lived use** | Synchronous `Connect` returns `TransportConnectOperation`; `OnReady`/`OnConnectFailed` permit an async client adapter over one shared engine | [SocketSet Redis mapping](socketset-public-api-map.md#stackexchangeredis-adapter-api), provider examples, and [higher-level adapters](api.md#higher-level-async-adapters) | Runtime does not own pooling, retry, request replay, or multiplexing. The consumer needs a small lease-backed receive owner/segment adapter, must copy when retention is unavailable, and retains outbound segments until terminal completion. |

## Cross-cutting acceptance mapping

| Concern | Contract | Evidence required |
|---|---|---|
| Buffer lifetime | Receive payload valid only during the ref-struct callback unless retained; retained sequence valid and unchanged until lease disposal, including after connection/engine shutdown; composed outbound memory owned by provider until logical write completion | Callback escape analysis, delayed lease disposal, nonblocking engine disposal, connection abort/provider shutdown, native completion, and slot/buffer reuse tests |
| Callback serialization | One connection's callbacks are serialized; different workers/connections may run concurrently | Reentrancy and multi-connection stress tests across every provider |
| Callback isolation | Application callback exception is contained to one connection; async TLS option work suspends only that handshake | Throwing/blocking callback and handshake-suspension tests |
| Accept backpressure | Each low-level `TransportListener.Accept` authorizes one native accept; Pipelines `AcceptAsync` submits demand instead of continuously draining the OS backlog | No-waiter tests, backlog saturation, cancellation races, bounded accept concurrency, and listener shutdown across providers |
| Terminal completion | Provider retains native state until final CQE/OVERLAPPED/callback completion; caller-owned `SendBorrowed` memory is releasable only after `OnWriteCompleted` | Cancellation-race, zero-copy notification, partial-write, and provider-shutdown stress tests |
| Backpressure | Adapter calls `TryPauseReceive` and later `ResumeReceive`; provider bounds already-completed and retained receives | Slow-consumer tests with memory bound, retained-lease exhaustion, fallback copying, and peer-side slowdown |
| Graceful close | Output drain -> TLS `close_notify` -> TCP write shutdown; reads may continue | Final-data-plus-EOF, close-notify, peer FIN, and abort tests |
| TLS parity | Every current option and callback is implemented, fallback-selected, or rejected | Matrix-driven tests and per-provider support report |
| Offload truthfulness | Request, negotiated TLS, kernel TX/RX, and hardware status remain distinct | Positive and negative activation probes; no flag-only success |
| Socket compatibility | Managed provider uses ordinary Socket/SAEA and the same callbacks | Plaintext/TLS parity, dispose, half-close, and cancellation tests |
| Client lifecycle | Provider/engine shared; connect operation correlated; reconnect outside runtime | Long-lived pipelining, server close, reconnect, and cancellation tests |

## Deliberately excluded

| Exclusion | Reason |
|---|---|
| UDP/datagrams | Read leases and ordered all-or-error writes are stream semantics. A datagram API needs message boundaries and endpoint-per-operation semantics. |
| QUIC | QUIC is multiplexed, encrypted, and message/stream oriented with an existing runtime API. |
| HTTP concerns | Protocol parsing, request scheduling, limits, and metrics belong above the runtime transport. |
| Automatic pooling/retry | Retry safety is protocol-specific; the transport cannot know whether an operation is replayable. |
| Portable NIC configuration | Requires administrative policy, driver support, routing knowledge, and platform-specific tooling. |
| Stable provider tuning | Typed provider options are experimental; remove knobs without demonstrated operator scenarios before stabilization. |
| Fake `Socket` or `SslStream` | A facade would misrepresent ownership and valid operations. |
